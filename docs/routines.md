# Routine prompts (claude.ai scheduled routines)

Three routines run on Ron's personal claude.ai plan against this repo: two standing (upstream-radar, upstream-digest) and one campaign-scoped (upstream-campaign, deleted when the ten-theme campaign closes). Registration is not execution: after creating one, set `data/health/sessions.json → routine_status.<name> = "REGISTERED"`; the first session to observe an evidenced fire (ledger line + commit) flips it to `"LIVE"` with the commit hash. The weekly smoke workflow watches for a LIVE radar going silent.

Wording rule (learned in Ron's system, binding): a repo-writing routine prompt is framed as the user's own standing authorized routine and never contains any instruction that could read as suppressing a notification channel.

## Hard-won operational rules (from the first real fires, 2026-08-29)

1. **Clone via add_repo, not plain git.** The cloud sandbox has no git credentials: a bare `git clone` fails with `could not read Username`. Call `mcp__Claude_Code_Remote__add_repo` (owner Ronkimhi, repo upstream, access push) first, then ONE inline `git clone --depth 1`, then `register_repo_root`.
2. **Commit and push BEFORE attempting the artifact republish.** In routine venues the publish can block on a permission prompt and strand the whole run. The first radar test fire wrote three real signal cards, validated, rebuilt the UI, and then froze on the publish prompt with nothing committed. Push first; republish last; a skip is normal.
3. **A blocked republish is not a failed run.** Record `artifact: skipped(<reason>)` and finish. The repo stays canonical; the next session that can publish refreshes the page.
4. **Triage artifact-changed notifications with `tools/queue_check.py`, not by hand.** Run `python3 tools/queue_check.py <version-id>`. Exit 0 means the publish is attributable to this repo's own committed build (the version's unix timestamp sits just after `app/index.html`'s `built_at` and a ledger line records that republish) and the 1.7 MB page read may be skipped; exit 1 means read the live page. It never reports the queue as empty, only as attributable, and it fails toward the read on anything it cannot parse. **A session that skips SAYS it skipped and why** — reporting "queue empty, checked" without fetching the page claims a check that did not run.

   The hand-applied timestamp heuristics this rule used to carry are deleted, and the deletion is the lesson: the gap between a version timestamp and `built_at` was written here as a 5-minute threshold and misclassified a 6.7-minute build as a click. Merge and triage rules live as code so one place can be fixed; prose copies of them drift and are re-derived by every session that reads them.

   - **The queue block is the only ground truth, but a read AFTER someone else's republish proves nothing.** Every build writes `{"v":1,"queue":[]}`, so a publish erases any click queued since the last build. The drainer reading afterwards sees an empty queue whether or not a click was destroyed. This is why CLAUDE.md's click-queue step 4 puts the check on the PUBLISHER: it is the only actor positioned to see the entry before it is overwritten. Reads by the drain seat catch only clicks that arrive after the most recent publish.
5. **A stand-down is a claim about disk, and needs disk evidence** (2026-08-31). Four campaign fires in a row read a ledger line saying a stage had run and stood down over a file that stage had never written. A ledger line records that a stage RAN, not that it SUCCEEDED. Open the file, look for the artifact the stage owes, and quote what you found.
